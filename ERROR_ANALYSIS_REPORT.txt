================================================================================
ERROR TYPE DEFINITIONS
================================================================================

1. RETRIEVAL FAILURE
   - Definition: The Knowledge Graph query returns no nodes, wrong nodes, or 
     falls back to a generic query that doesn't address the user's question.
   - Symptoms: Empty baseline results, mismatched entities, fallback query used
   - Root causes: Entity resolution failure, missing data in KG, unsupported query type
   
2. CONTEXT OVERLOAD/NOISE
   - Definition: Too much irrelevant context is provided to the LLM, diluting 
     the signal and making it hard to extract the relevant answer.
   - Symptoms: Large result sets, low relevance scores, mixed/unrelated players
   - Root causes: Overly broad queries, ambiguous criteria, no filtering

3. LLM HALLUCINATION
   - Definition: The LLM's answer contains information NOT supported by the 
     retrieved context, invented from its parametric knowledge.
   - Symptoms: Facts not in context, confident wrong answers, out-of-scope claims
   - Root causes: LLM ignoring grounding instructions, filling gaps with training data

4. POOR SYNTHESIS
   - Definition: The retrieved facts are correct, but the LLM fails to properly 
     combine, calculate, or reason over them to produce a coherent answer.
   - Symptoms: Wrong calculations, incomplete comparisons, missed logical connections
   - Root causes: Complex multi-step reasoning, numerical aggregation errors

================================================================================
RECOMMENDATIONS FOR IMPROVEMENT
================================================================================

1. RETRIEVAL FAILURE MITIGATION:
   - Implement fuzzy matching for player names (Levenshtein distance)
   - Add nickname/alias lookup table (already working for CR7)
   - Return explicit "data not found" signal for missing attributes
   - Add per-season breakdown queries for comparison requests
   - Add monthly/gameweek date filtering support

2. CONTEXT OVERLOAD MITIGATION:
   - Current LIMIT 10 constraint is working well
   - Consider dynamic limits based on query complexity
   - Add query decomposition for multi-part questions

3. HALLUCINATION MITIGATION:
   - Strengthen grounding in prompts (DONE - updated priority_note)
   - Add explicit "only use provided context" constraints
   - Consider post-generation fact verification
   - Flag out-of-scope queries before LLM processing
   - Consider switching from Mistral (high hallucination rate)

4. POOR SYNTHESIS MITIGATION:
   - Pre-compute aggregations in KG layer (grouped totals)
   - Add chain-of-thought prompting for calculations
   - Return data in formats that support requested operations
   - Include matches_played whenever total_points is returned

5. PREPROCESSING IMPROVEMENTS:
   - Better handling of misspellings (fuzzy entity matching)
   - Detect temporal granularity requests (month, week)
   - Identify out-of-scope attributes (salary, nationality, etc.)
   - Parse "improvement" queries to return per-period data

================================================================================
CONCLUSION
================================================================================

The FPL RAG system performs well on straightforward queries but struggles with:
1. Out-of-scope attributes (salary, CL goals, nationality)
2. Temporal granularity beyond seasons/gameweeks
3. Cross-season improvement calculations (needs per-season data)
4. Entity resolution for misspellings (but handles nicknames well)

The LLM layer shows significant variation:
- GPT-OSS and Gemma exhibit strong grounding behavior
- Mistral frequently hallucinates and makes arithmetic errors
- All LLMs benefit from the updated prompt emphasizing baseline data

Key insight: Most "hallucinations" stem from retrieval returning WRONG data
(e.g., PL goals when CL asked) rather than LLMs inventing facts. Improving
retrieval precision and adding scope detection would prevent most errors.
